# invoice-pipeline — 开票全流程主编排

把第 4/5/7/8 步的四个子 skill 串成一条管道，在第 6 步（税务局开票）处产出开票信息卡并暂停，等人工开完票返回 PDF 后继续。

> 📌 **本 skill 属于开票自动化 7-Skill 集合**：完整清单、依赖关系、handoff 交接契约、部署位置与构建产物说明，见 **`~/.workbuddy/skills/MANIFEST.md`**（集中串联件）。本编排是本集合下游 4 个 skill 的唯一调用入口。

## 完整 8 步流程定位

| 步骤 | 环节 | 负责 | 本编排是否调用 |
|---|---|---|---|
| 1-3 | 邮件检测 / 判断打回 / 接收表格 | 上游（非本项目） | ✗ 输入来自这里 |
| **4** | 企微文档查重 | wecom-invoice-query | ✅ 阶段 1 |
| **5** | 兴趣岛订单核验 | order-invoice-checker | ✅ 阶段 2 |
| 6 | 税务局开票（扫码单设备登录） | **人工** | ⭐ 阶段 3 出卡片暂停 |
| **7** | 兴趣岛新建发票记录 | invoice-create | ✅ 阶段 4（需 PDF） |
| **8** | 企微文档归档 | wecom-invoice-import | ✅ 阶段 5 |

## 何时使用

用户传入**上游邮件解析 skill 输出的发票邮件报告（.json 结构化首选 / .md 人视图兜底）**、**开票信息申请表格（Excel）**或**粘贴一段开票信息文本**，要求跑开票流程时。典型说法：「跑一单开票」「开票流程」「把这些订单开票」「发票管道」「处理今天的发票邮件报告」。

## 输入格式

四种均可，阶段 0 自动识别：

### 1. .json 文档（上游邮件解析 skill 输出，**首选**）

文件名：`[YYYY.M.D]_[HH-mm]_发票邮件报告.json`。

**结构化、字段零歧义**，阶段 0 直接 `json.load` 消费，无需解析文本。结构见下方阶段 0 解析逻辑 A'。同一封邮件若 `.json` 与 `.md` 同时存在，**优先用 `.json`**。

### 2. .md 文档（上游邮件解析 skill 输出，兜底人视图）

文件名：`[YYYY.M.D]_[HH-mm]_发票邮件报告.md`。

含 5 段：报告头（元信息）/ 加急订单 / 正常订单 / 订单号异常 / 疑似不确定邮件。仅在无对应 `.json` 时使用，阶段 0 走文本解析（见逻辑 A）。

### 3. Excel 表格

含订单号、抬头、抬头类型、税号（企业）、金额、项目名称。

### 4. 粘贴文本

直接粘贴一条或多条开票信息，字段同 Excel。

### 必填字段（每条进入流水线的记录）

- 订单号（交易单号，step 4/5/7/8 都用）
- 抬头（购买方名称）
- 抬头类型（个人/企业）— 决定是否需要税号
- 金额（含税）
- 项目名称（开票项目）

企业抬头额外必填：统一社会信用代码（税号）。

> ✅ **字段缺口已闭合**：上游 .json（及 .md）现已包含 发票抬头/税号。剩余字段处理：
> - 抬头类型（个人/企业）→ 阶段 0 根据税号有无推断（有税号=企业，无=个人）
> - 项目名称 → 不需要，invoice-create 会按订单号自动填充（所属品类/商品名称/用户ID）
> - 若 .json/.md 中 `title`/`tax_id` 为空（表格未含该列或配置缺失）→ 阶段 3 出卡片前向用户确认

## 管道流程（6 阶段）

### 阶段 0：解析输入

按输入类型分流解析，输出结构化记录列表 + 异常/不确定告警。

**输入识别**：根据用户提供的内容判断——`.json` 文件路径 → 走 .json 解析（首选）；`.md` 文件路径 → 走 .md 解析（兜底）；`.xlsx` → 走 Excel 解析；纯文本 → 走粘贴解析。

#### A'. .json 解析逻辑（首选，字段零歧义）

直接 `json.load` 读取，无需文本解析。按顶层字段分派：

| 顶层字段 | 分派到 | 处理 |
|---|---|---|
| `urgent_orders` | `to_process`（priority=urgent） | 其中 `is_valid == true` 进流水线；`is_valid == false` 归入 abnormal_orders |
| `normal_orders` | `to_process`（priority=normal） | 同上 |
| `invalid_orders` | `abnormal_orders` | 仅告警，不进流水线（订单号不可用） |
| `uncertain_entries` | `uncertain_emails` | 仅告警，不进流水线 |
| `failed_entries` | 解析失败告警 | 仅告警 |

**字段映射**（json 字段 → 结构化字段）：

| json 字段 | 结构化字段 | 备注 |
|---|---|---|
| `order_id_cleaned` | `order_id` | |
| `amount_raw` | `amount` | 原始字符串，按需转数字 |
| `note` | `remarks` | |
| `title` | `抬头` | |
| `tax_id` | `税号` | |
| `message_subject` | `email_subject` | |
| `message_sender` | `sender` | |
| `message_date` | `email_time` | |
| `quadrant` / `is_valid` | 校验状态 | 决定该记录是否进流水线 |
| （由所在数组） | `priority` | urgent_orders→urgent，normal_orders→normal |

> 抬头类型（个人/企业）由阶段 0 根据 `tax_id` 有无推断；项目名称由 invoice-create 按订单号自动填充，无需上游提供。

#### A. .md 解析逻辑（兜底，5 段拆分 + 字段提取）

.md 文档按 markdown 标题（`##`）拆成 5 段，逐段处理：

| 段 | 标题关键词 | 处理方式 |
|---|---|---|
| ① 报告头 | `发票邮件筛选报告` | 提取运行时间 + 各类计数（加急 A / 正常 B / 异常 C / 不确定 D），写入 meta |
| ② 加急订单 | `加急` | 每行提取为记录，标记 `priority: 'urgent'`，进入流水线 |
| ③ 正常订单 | `正常` | 每行提取为记录，标记 `priority: 'normal'`，进入流水线 |
| ④ 订单号异常 | `订单号异常` | 仅收集，**不进流水线**（订单号不可用，无法自动核验） |
| ⑤ 疑似不确定邮件 | `不确定` | 仅收集，**不进流水线**（邮件性质待人工判断） |

**字段提取**（② 加急 / ③ 正常订单表，按列映射）：

| .md 列 | 结构化字段 |
|---|---|
| 订单号 | `order_id` |
| 开票金额 | `amount` |
| 备注 | `remarks` |
| 发票抬头 | `title`（上游已扩展提取） |
| 税号 | `tax_id`（上游已扩展提取） |
| 来源邮件主题 | `email_subject` |
| 发件人 | `sender` |
| 邮件时间 | `email_time` |

> 抬头类型（个人/企业）由阶段 0 根据税号有无推断；项目名称由 invoice-create 按订单号自动填充，无需上游提供。

**④ 订单号异常**提取：订单号原文 / 清洗后数字 / 异常原因 / 开票金额 / 备注 / 来源邮件主题 / 发件人 / 邮件时间

**⑤ 疑似不确定邮件**提取：邮件主题 / 发件人 / 邮件时间 / 不确定原因

#### B. Excel / 粘贴文本解析

按原逻辑提取每条记录的 订单号/抬头/抬头类型/税号/金额/项目名称，统一标记 `priority: 'normal'`（Excel/粘贴无加急概念）。

#### 处理顺序

**加急订单 → 正常订单**。先处理全部 urgent，再处理 normal。每批内部可并行跑阶段 1-2。

**异常/不确定邮件**：阶段 0 末尾统一告警给用户（列出条数 + 明细摘要），**不进入阶段 1-5**。告知用户这些需人工处理。

#### 输出结构

```
{
  meta: { 运行时间, 加急: A, 正常: B, 异常: C, 不确定: D, 输入类型: 'md'|'excel'|'text' },
  to_process: [
    { order_id, amount, remarks, email_subject, sender, email_time,
      priority: 'urgent'|'normal',
      抬头, 抬头类型, 税号, 项目名称  // .md 输入可能为空，需补齐
    },
    ...
  ],  // 按 urgent 在前、normal 在后排序
  abnormal_orders: [ { 原文, 清洗后, 异常原因, amount, ... } ],     // 仅告警
  uncertain_emails: [ { 邮件主题, 发件人, 邮件时间, 不确定原因 } ]   // 仅告警
}
```

`to_process` 先经阶段 0.5 人工确认，确认后的进入阶段 1。多条记录时，先全部跑完阶段 1-2（查重+核验），再统一出卡片。

### 阶段 0.5：人工预览断点 ⭐（开票前确认）

阶段 0 解析完成后、查重前，先输出 md 报告让用户过目本轮要处理的邮件，再弹选择框确认是否开票。

**步骤**：

1. **输出 md 报告**：告知用户 md 报告路径（上游实际生成的文件名带时间：`<reports>/[YYYY.M.D]_[HH-mm]_发票邮件报告.md`，如 `2026.8.6_14-42_发票邮件报告.md`），提示「可打开 md 文件查看完整邮件信息（含正文、抬头、税号等）」。

2. **分流**：将 to_process 分为两组：
   - **达标邮件**：字段齐全（`title`/`tax_id` 非空）、判定明确、订单号合法 → 批量问
   - **异常邮件**：字段缺失 / 不确定 / 订单号异常 → 逐封单独问

3. **达标邮件批量问**（一次选择框覆盖全部达标邮件）：
   - question 嵌入每封的「订单号 / 抬头简称 / 金额 / 优先级」，并附「可打开 md 报告查看完整邮件信息：{md_path}」
   - 选项：
     - `全部确认，继续开票`（推荐）— 全部进入阶段 1 查重
     - `全部跳过` — 全部标记跳过，不处理
     - `逐封确认` — 逐封单独弹选择框
     - `全部标记待人工` — 全部列入人工待办

4. **异常邮件逐封单独问**（每封一个选择框）：
   - **字段缺失**（`title` 或 `tax_id` 为空）：question 注明缺哪个字段 + 提醒可打开 md 查看；选项：`我来补齐后继续` / `跳过本封` / `标记待人工`
   - **不确定邮件**：question 注明 uncertain 原因 + 提醒可打开 md 查看；选项：`是开票邮件，继续` / `不是，跳过` / `标记待人工`

5. **分流结果**：
   - 确认（含补齐后）→ 进入阶段 1 查重
   - 跳过 → 标记归档，不进后续阶段
   - 标记待人工 → 列入人工待办，不进后续阶段

> 边界：本轮只有 1 封达标且无异常 → 仍走批量问（选项简化为：确认继续 / 跳过 / 标记待人工）。全部是异常无达标 → 跳过批量问，直接逐封问异常。

### 阶段 1：查重（调用 wecom-invoice-query，step 4）

对每条记录的订单号，调用 `wecom-invoice-query` skill 查企微文档是否已开过票。

- **已开票** → 标记 `已开过，跳过`，不进入后续阶段
- **未开票** → 继续

### 阶段 2：订单核验（调用 order-invoice-checker，step 5）

对未开票的记录，调用 `order-invoice-checker` skill 核验兴趣岛订单状态。

- **已开票** → 标记 `系统已开票，跳过`
- **未开票** → 继续
- **需人工** → 标记并提醒

### 阶段 3：出卡片 + 暂停 ⭐（step 6 人工断点）

对通过核验的记录，**在聊天里渲染开票信息卡**（模板见下方），然后 **STOP**。

告知用户：「以上是 N 张待开票信息卡，请拿去税务局开票。开好后把发票 PDF 发回来，我继续帮你录入兴趣岛系统并归档企微文档。」

**此阶段必须暂停，不要继续阶段 4。** 等用户返回 PDF 才恢复。

### 阶段 4：等 PDF + 新建记录（调用 invoice-create，step 7）

用户返回开好的发票 PDF 后，对每条记录调用 `invoice-create` skill：

- 传入：订单号、开票金额、发票类型、抬头类型、发票抬头、企业税号（企业才有）、**`invoice_pdf_base64`（PDF 文件需先 base64 编码，沙箱无法读磁盘二进制）** 与可选的 `invoice_pdf_name`
- **⚠️ 安全门**：`confirm` 默认 `false`，只填不提交。需用户**显式确认**「可以点确定了」才传 `confirm=true`
- 输出：填好的截图 + `confirm_executed` 状态

### 阶段 5：归档（调用 wecom-invoice-import，step 8）

对已新建记录的订单，调用 `wecom-invoice-import` skill，把开票记录录入企微文档归档。

- 输入：开票记录 Excel（或结构化数据）
- 输出：录入成功 / 失败

### 最终输出

汇总报告：每条订单的状态（已跳过 / 已开票 / 已录入）+ 操作记录。

## 开票信息卡模板（阶段 3 渲染）

每条待开票记录渲染一张卡，4 个分区对应税务局界面：

```
📋 发票开票信息卡 — 订单号 {订单号}

① 购买方信息
  • 名称（抬头）：{抬头}              *必填
  • 税号：{企业填税号 / 个人不填}      *仅企业必填
  ✗ 不填：地址 · 电话 · 开户银行 · 银行账号

② 开票项目信息
  • 项目名称：{项目名称}              *必填
  • 金额（含税）：¥ {金额}            *必填
  ✗ 不填：规格型号 · 单位 · 数量 · 单价 · 税额
  ⓘ 税率选默认即可

③ 支付信息
  • 支付渠道：不填，留空
  • 交易单号（订单号）：{订单号}       *必填

④ 备注信息
  • 备注：订单号 {订单号}             *必填

销售方信息已预填，无需操作。
```

**判断规则**：
- 抬头含「个人」/「自然人」→ 税号不填
- 抬头是企业 → 税号必填
- 订单号填 2 次（交易单号 + 备注），必须一致

## 暂停 / 恢复机制

本编排是**多轮对话**，不是单次脚本执行：

1. 阶段 0-2 跑完后，阶段 3 渲染卡片并**停止本轮回复**
2. 用户去税务局开票（可能几分钟到几小时）
3. 用户回来发「开好了」+ 附上 PDF → 触发阶段 4 恢复
4. 阶段 4-5 自动跑完

**不要在阶段 3 后自作主张继续。** 第 6 步必须人工，PDF 是阶段 4 的硬依赖。

## 性能优化（执行时务必遵守）

编排层最浪费时间的不是逻辑本身，是浏览器/SPA 启动 + 盲等 + 重复扫描。以下是已落地的提速点：

1. **阶段 1 与阶段 2 可并行**：`wecom-invoice-query`（步骤4）跑在 `wecom` 命名浏览器实例，`order-invoice-checker`（步骤5）跑在 `interest-island` 命名浏览器实例——**两个独立进程、互不抢占**。单条订单的查重与核验可同时发起（两个后台 `dev-browser` 任务并行），整体耗时从"两者相加"降到"取大值"。批量订单时同样可并行。**这是编排层最大的提速点**，执行时不要串行等完一个再跑下一个。

2. **子 skill 已修复 `main().then()` 异步截断**：`order-invoice-checker` / `invoice-create` 的运行入口已统一改为顶层 `await main()`，避免 QuickJS 沙箱里 `main().then()` 被脚本退出截断、只打印 `START` 就死的坑（曾经导致"跑死→改→重跑"白费一轮）。

3. **wecom 子 skill 已把盲等改条件轮询**：`wecom-invoice-query` / `wecom-invoice-import` 打开/刷新企微文档时改用 `waitForAppReady()` 轮询 `SpreadsheetApp.workbook`，就绪即返回（通常 3-5s），不再固定 `waitForTimeout(12000)` 盲等，每次省 7-9s。

4. **wecom 子 skill 已落实"全表只扫一次"**：重复检查、抽查、全量取号合并为一次 `evaluate`，结果复用，不再对 5000+ 行表反复扫描。

## 注意事项

1. **安全门优先**：invoice-create 的 `confirm` 永远默认 false，除非用户显式说「可以提交了」
2. **税号判断**：抬头类型决定是否填税号，阶段 3 卡片必须正确标注
3. **PDF 是硬依赖**：阶段 4 没有 PDF 无法进行，必须等用户返回
4. **查重优先**：阶段 1 查到已开票直接跳过，避免重复开票
5. **Windows 路径**：子 skill 脚本里用单反斜杠，双反斜杠会静默崩溃
6. **加急优先**：.md 输入时，加急订单先于正常订单处理（阶段 0 已按 urgent→normal 排序）
7. **异常/不确定邮件不进流水线**：订单号异常与疑似不确定邮件仅告警，由人工处理，不调用阶段 1-5
8. **字段缺口**：上游 .json/.md 已含抬头/税号。若某记录 `title`/`tax_id` 仍为空（表格未含该列或配置缺失）→ 阶段 3 出卡片前向用户确认补齐，否则卡片不完整无法开票
